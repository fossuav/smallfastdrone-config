## Status: Phase 3 in progress; Phase 7 (SFD enablement) is the new priority

**Strategic pivot, 2026-08-27.** A credible competing configurator means generic configuration is no longer where this tool wins. Two consequences, now written into PLAN.md:

- **Configure, don't ask** — where the tool can determine the right setting, it sets it rather than surfacing a control.
- **The wizard library is the product**, particularly on-drone (Lua) wizards.

Both depend on **SFD enablement**: provisioning a drone with a per-drone identity key so SFD can ship applets only that airframe can decrypt. The architecture is designed and written up in [docs/SECURITY.md](docs/SECURITY.md) (decisions 32–34 in PLAN.md); implementation is Phase 7 and jumps ahead of Phases 4 and 6. Nothing is built yet.

## Recent log

- 2026-08-28: **Phase 7 slice 1 — save your drone's settings.** First code of the SFD-enablement arc, and the piece with no firmware dependency. New pure module `src/workflow/param-backup.ts` builds a snapshot document from the live param map (`buildBackup`), renders it (`serializeBackup`), reads one back with operator-readable errors (`parseBackup`), and names the file (`backupFilename`). Document is `sfd-param-backup/1`: schema + `createdAt` + a vehicle block (sysid, firmware version, frame label, FC uid — all present as `null` rather than absent, so a reader never distinguishes "missing" from "unknown") + params keyed by name. Params are sorted on the way out so two backups of the same drone diff cleanly in any text tool, and the param **index is dropped** — indexes shift between firmware builds, so name is the only stable key. `parseBackup` throws rather than returning null (every caller has to stop and tell the operator what's wrong) and distinguishes "not a backup" from "a backup from a newer version of this tool", refusing to salvage a shape it doesn't know.

  **A backup holds the delta, not the whole parameter set** (operator decision): only parameters the drone reports as changed from its factory default, minus read-only ones. That delta *is* the configuration, it restores cleanly onto freshly-flashed firmware that boots at defaults, and it keeps a backup at tens of entries rather than ~1400. Getting the defaults needed new plumbing — **`src/protocol/param-pack.ts`**, a parser for ArduPilot's packed parameter file served over MAVLink-FTP at `@PARAM/param.pck?withdefaults=1`. That file is the *only* authoritative source: defaults are board- and frame-specific, and ArduPilot's param metadata carries `ReadOnly` but **no `Default` field at all**. Neatly, the firmware attaches a default to an entry only when the current value differs from it, so "has a default attached" reads directly as "the operator changed this" — the FC computes the filter for us. The read-only half comes from metadata: `scripts/build-param-metadata.py` now keeps `ReadOnly` (45 params) and `params.ts` grew `isParamReadOnly()`; `src/protocol/param-metadata.json` regenerated. On SITL that filter turns 1396 parameters into 28 changed, then 17 saved — and the 11 it drops are exactly right: `COMPASS_DEV_ID*` and `BARO*_DEVID` (sensor identity, belongs to detected hardware), `BARO*_GND_PRESS` (a live calibration reading), `STAT_BOOTCNT` (the drone's own bookkeeping). Read-only turned out to cover most of the hand-maintained deny-list that had been sketched for restore.

  UI is a "Your drone's settings" card on `SettingsView`, matching the settings-vs-procedures rule in docs/UX.md (a setting-shaped action, so an inline control, not a wizard). Save is a plain anchor download rather than the File System Access API: a one-shot export of a small document, where a save dialog would add a permission prompt for no benefit, and the result line names the file so the operator knows what to look for. No composable — one consumer, so the download helper is inline per the premature-abstraction rule in docs/CODING-STANDARDS.md. Unit tests cover the round trip (float precision, negatives, zero), every reject path, filename stamping, and the filter; `test/unit/param-pack.spec.ts` pins the wire format with synthesised packs plus **a real 1396-param capture from SITL** (`test/unit/fixtures/param-pck-sitl.bin`) so a misreading of the C++ can't pass. E2E clicks Save, captures the actual download, and asserts the file on disk — a small delta, sorted, numeric, with no read-only entries — because asserting the success banner alone would pass with an empty file.
- 2026-08-27: **SFD enablement architecture — designed and written up (no code).** Strategic pivot: with a credible competing configurator emerging, the tool's differentiation moves from generic configuration to what only an SFD-enabled drone can do — "configure, don't ask" plus a deep on-drone wizard library, both gated on being able to ship Lua that only the customer's own airframe can decrypt. Read the `pr-lua-encryption` branch in `../smallfastdrone/` (12 commits) and designed the enablement architecture on top of it. **Key findings from the existing branch:** `.lxa` v1 encrypts with `public_key[3]` — a *public* key embedded in every firmware image, so publishing a binary publishes the key; `GET_PUBLIC_KEYS` `memcpy`s raw slot bytes into a MAVLink reply, so a secret stored there would be readable by anyone holding an upstream ArduPilot signing key; `set_public_keys()` packs non-zero keys toward the front while `encrypt_script()` hard-codes index 3 (guaranteed to collide in the target end state); `create_nonce()` is called on the *decrypt* path where it overwrites the file's nonce, and passes `nonce_len` uninitialised to `get_system_id_unformatted(buf, len)` where `len` is in/out — so the UUID-binding path cannot work as written (it defaults off). Also confirmed the Lua sandbox already blocks the co-tenancy leak: `string.dump` is commented out of `strlib` and `package`/`coroutine`/`os`/`debug` are all disabled in `linit.c`. **The design:** per-drone X25519 identity **generated on the drone** from the hardware TRNG, private half never emitted — because the customer's laptop is untrusted, any key we *deliver* has passed through their hands. SFD encrypts each applet to that public key via ephemeral-static ECDH, with the ephemeral *derived* from an SFD master secret + drone identity + applet content hash so every shipped artefact is reproducible without a key database (which is what keeps the design serverless). `.lxa` v2 adds the ephemeral public key and puts the STM32 UID in the nonce prefix as a second, independent gate. **Key custody is build-time**, via the existing `build_bootloaders.py --omit-ardupilot-keys` — this supersedes an earlier sketch that had the configurator do `SET_PUBLIC_KEYS` then `REMOVE_PUBLIC_KEYS` at enable time, which would have required the customer's tool to hold an SFD *private* key. It also moots the upstream `all_zero_keys() → check_signature() == true` fail-open trap, since the key array is never mutated. **The exit ceremony** is non-negotiable and shaped by silicon: RDP 1→0 mass-erases, which is also the security property — no state exists where the customer holds both an unlocked chip and a live key. Unlock never requires an SFD signature, which is both the customer's escape hatch and the GPLv3 §6 anti-tivoization position.
